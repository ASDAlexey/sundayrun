# Архитектура

Веб-приложение клуба «Воскресный парковый пробег» (Таганрог, КЛБ «Легенда»): организатор загружает Excel-экспорт секундомера → приложение определяет пол участников, считает места, генерирует PDF-протокол по образцу `assets/20.09.2020.pdf` и публикует данные в GitHub. Сайт показывает архив протоколов, а из накопленной истории считаются примечания, рекорды, рейтинг и остальная статистика.

## Жёсткие требования

- **Всё 100% бесплатно**: без бэкенда, без платных сервисов. Бесплатные OSS-пакеты разрешены.
- Вся логика — на клиенте (браузер). Хостинг и хранилище — GitHub.
- UI: русский приоритетный (source locale `ru`), английский — перевод.
- Стек и дизайн — как в проекте `portfolio`: Angular 22, zoneless, signals, дизайн-система Litely, Bun, Vitest (покрытие 100%).

## Поток данных

```
xlsx (экспорт секундомера)
  → xlsx-reader (fflate + DOMParser)          — ZIP+XML → string[][]
  → timer-export-parser                       — → Participant[] (скип NOTE!, DNF, круги)
  → gender-inference                          — пол по имени (словарь + эвристики) + ручная правка
  → name-order                                — автофикс порядка «Имя Фамилия» по архиву и словарю
  → protocol-builder (+ notes-builder)        — места по полу, авто-примечания из истории
  → protocol-doc-definition → pdfmake         — PDF (PT Serif, кириллица) → Blob
  → protocol-db-write (applyEventsToDb)       — вклад забега накатывается на sundayrun.db
  → github-storage (Git Data API)             — атомарный коммит данных в репозиторий sundayrun
  → version-pointer                           — второй мини-коммит: data/version.json → SHA данных
```

## Входные данные (проверено на реальных файлах)

- xlsx из LibreOffice, один лист, колонки A–F: `Name, Total, Avg/lap, Avg/km, Lap 1, Lap 2`.
- Времена — **текст** вида `0:19:03,028`. В конце листа мусорный блок «NOTE!» — пропускается.
- **Колонки пола нет** — пол определяется по имени (второй токен «Фамилия Имя») со степенью уверенности; неуверенные строки подсвечиваются для ручной правки.
- Семантика кругов: 2 круга → финишировал 5 км (круг 1 = отсечка 2,3 км); 1 круг → бежал только 2,3 км; нет времени → DNF.
- Метаданных события (№, дата, место) в xlsx нет — вводятся в форме. При мультизагрузке каждый файл получает свой черновик реквизитов.

## Выходной PDF

A4 «ПРОТОКОЛ» по образцу: шапка (дата, «Воскресный парковый пробег № N», город, парк, клуб), вводный абзац, таблица «Участники» (№, Спортсмен, Время 2,3/5 км, Пол, Место М/Ж, Клуб, Участий, Примечание), сокращения DNF/DSQ, подпись председателя. Шрифт PT Serif (OFL, кириллица).

## Хранилище: папка `data/` в репозитории приложения `sundayrun`

Код и данные живут в одном публичном репозитории (решение пользователя, 2026-07-05):
данные — под `data/`, пути собраны в `protocols-repo.constant.ts` (`DATA_DIRECTORY`).
Компромисс: PAT организатора имеет запись во весь репозиторий, включая код.

```
data/
  sundayrun.db                # ЕДИНСТВЕННЫЙ источник истины: события, участники,
                              # результаты, материализованные сводки, погода
  version.json                # указатель: {schemaVersion, sha} — commit SHA актуальных данных
  site-meta.json              # объявление организатора: время старта + сообщение на главной
  events/2026-06-14/
    source.xlsx               # исходный Excel — сырьё для пересборки БД
```

JSON-зеркала (`index.json`, `athletes.json`, `events/*/results.json`) удалены — план и мотивация
в [DB_ONLY_MIGRATION.md](./DB_ONLY_MIGRATION.md). Единственный источник = БД: и рантайм, и
пререндер, и админ-импорт читают её. Сырьё для аварийной пересборки — `source.xlsx` плюс история
самого `.db` в git.

PDF-протокол в репозитории **не хранится** — он собирается на лету из данных БД тем же
`pdfmake`-пайплайном, что и при публикации (`pdf/protocol-pdf.service.ts`), по кнопке «PDF»
на карточках и странице протокола. Так файл всегда соответствует данным, а репозиторий
не раздувается бинарниками.

Импортированная история (249 забегов с 2019 г.): сезон 1 — из текстовых PDF
`assets/parkrun-pdfs/`, сезон 2 — с фото-протоколов VK (PDF собраны в
`assets/parkrun-pdfs/результат/`). У импортированных событий нет `source.xlsx`.
Нет протоколов: № 258 (06.11.2022), № 2.60 (30.11.2025), № 2.66 (11.01.2026).

- **Запись**: из браузера через GitHub **Git Data API** (blobs → tree → commit → update ref) — `source.xlsx` каждого забега партии и пересобранная `sundayrun.db` в **одном атомарном коммите**; конфликт ref → refetch + retry, причём БД перечитывается на каждой попытке, поэтому параллельная публикация мержится, а не затирается. Сразу за ним — второй мини-коммит с `version.json` (указатель на созданный коммит данных, с ретраями: ветка может отставать на такт). Организатор один раз вставляет fine-grained PAT (scope: только репозиторий `sundayrun`, Contents read/write); хранится в localStorage; при 401 — баннер «токен истёк».
- **Мультизагрузка**: `publishEvents` кладёт всю партию в один коммит — публикация всё-или-ничего; события внутри сортируются по дате, поэтому примечания цепочкой считаются в хронологическом порядке.
- **Статистика пересчитывается автоматически** при каждой публикации (`applyEventsToDb`): вклад этой даты сначала снимается, потом накатывается заново — перепубликация идемпотентна. Пересчитываются рекорды атлетов (за всё время и по годам), агрегаты забега (финишёры, среднее, лучшие и медианы М/Ж), материализованные сводки (`overall_stats`, счётчики финишей) и авто-примечания. Погода на 9:00 у трассы подтягивается из Open-Meteo один раз на публикацию (сбой → публикуем без погоды). Вручную после публикации ничего пересчитывать не нужно.
- **Удаление забега** (`delete-event.ts`, зеркало публикации): один атомарный коммит удаляет `source.xlsx` события и перезаписывает `sundayrun.db` уже без его вклада — рекорды и сводки пересчитываются по оставшимся забегам, — затем идёт тот же коммит-указатель. Если указатель не закоммитился после ретраев, удаление считается выполненным, но «отстающим» (`pointerPublished: false`) — повторный запуск идемпотентен. UI — блок удаления на `/admin`: виртуальный список опубликованных забегов с поиском и подтверждением «Точно удалить» (`EventDeleteService`).
- **Чтение** (архив, история, статистика): без токена из `sundayrun.db` HTTP-range-запросами. JSON-фолбэка больше нет: транзиентный сбой range'а переоткрывает пул и повторяет запрос один раз (`PROTOCOL_DB_QUERY_ATTEMPTS`), устойчивый — уходит в error-state с кнопкой перезагрузки. Публичные страницы вдобавок пререндерены (см. ниже), поэтому первый экран не зависит от БД вовсе. `raw.githubusercontent.com` для массовых данных не используем — блокируется в РФ.
  - **БД читается с того же origin (GitHub Pages)**, куда её кладёт билд (`angular.json` assets → `data/sundayrun.db`), и открывается относительно base href (`ProtocolDbService.#dbUrl` через `inject(DOCUMENT).baseURI`, как self-hosted шрифты/wasm). Причина: **все публичные GitHub-CDN ломают range-чтение SQLite** — jsDelivr отдаёт range поверх brotli-сжатого файла (`content-range` = сжатый размер → `Invalid HTTP response`), statically виснет на глубоких offset'ах, githack отдаёт 403 на HEAD (а `sqlite-wasm-http` берёт размер через HEAD). Собственный хост Pages (Fastly) отдаёт чистые range'ы; правда, и он гзипит HEAD-ответ, из-за чего размер файла читается неверно — это пропатчено esbuild-плагином в `scripts/build-sqlite-assets.ts`. Локальный dev читает БД прямо с dev-сервера (см. `environment.development.ts`).
  - **Cache-busting — через имя файла, не query.** SQLite парсит цель `open()` как URI и срезает `?…` до VFS, поэтому `?v=` до HTTP не доходит. Вместо этого CI кладёт в деплой копию, названную по SHA данных (`data/sundayrun-<sha>.db`), — иммутабельный URL, который никакой кэш не может отдать протухшим. Плоское имя остаётся фолбэком на время деплоя.
  - **Свежесть данных** (`DbFreshnessService`): указатель `version.json` двигается сразу после публикации, а sha-копия БД появляется только когда доедет деплой (~3–5 минут). Пока проба sha-URL отдаёт 404, приложение читает плоскую копию (прошлые данные, полностью рабочие), а в шапке висит баннер «результаты обновляются» с таймером; фоновой поллинг превращает его в предложение перезагрузиться. Вердикт «Fresh» дополнительно перечитывает указатель с cache-busting-параметром — raw может отставать до пяти минут, и свежий SHA оттуда запоминается в sessionStorage на несколько минут (`CdnRefService.noteFreshSha`), чтобы сессия после перезагрузки не откатилась к тому же протухшему ответу.
- **Указатель версии** (`CdnRefService`): все data-URL пинятся к commit SHA, а сам SHA берётся из `data/version.json`. Указатель читается с **raw.githubusercontent** (жёсткий пятиминутный предел кэша), а не с jsDelivr, чей origin наблюдался отдающим протухший указатель даже после успешного purge. Цепочка фолбэков: запомненный свежий SHA → указатель → branch head через GitHub API (не кэшируется) → литеральная ветка. После публикации или удаления `pin` подставляет только что созданный коммит, чтобы сессия сразу видела свою запись.
- **Авто-примечания** считаются из истории БД: «Первое участие», «ЛР (было X)» (с датой прежнего результата и ссылкой на тот забег на вебе), «Лучший результат YYYY г.». На `/preview` они подставляются автоматически при открытии; история отсекается до даты события (`historyBeforeDate`), поэтому доимпорт и перепубликация не сравнивают атлета с будущими результатами. Админ-импорт (`github/history.service.ts`) качает БД **целиком через авторизованный Contents API**: при серийной загрузке старых файлов CDN отдал бы устаревшую копию.
- **Объявление на главной**: организатор на `/admin` задаёт время старта и сообщение; `site-meta.json` коммитится тем же Git Data API одним файлом (`publish-site-meta.ts`, `site-meta.service.ts`) с purge CDN-пути. Это единственные данные, которые до сих пор читаются с jsDelivr (файл крошечный, range не нужен); 404/403 или сетевая ошибка — блок просто скрыт.

### Как почистить кэш jsDelivr вручную

jsDelivr кэширует файлы ветки `@main` до недели (`max-age=604800`). Через jsDelivr сейчас идут
только `version.json` (purge после публикации) и `site-meta.json`. Приложение дергает purge само,
но если файл в репозитории поменяли **руками** (прямой пуш, переименование, ручная правка) —
сброс делается `curl`'ом того же пути на `purge.jsdelivr.net` вместо `cdn.jsdelivr.net`:

```bash
curl 'https://purge.jsdelivr.net/gh/ASDAlexey/sundayrun@main/data/version.json'
```

Ответ `"status": "finished"` — запрос принят. **Важно:** URL пурджа должен **точно совпадать** с
тем, что запрашивает приложение — **вместе с `@main`**. jsDelivr держит `@main/data/version.json` и
`/data/version.json` (без версии) как **разные ключи кэша**, поэтому пурдж без `@main` не сбросит
ветковый кэш. Проверить, что взлетело:

```bash
curl -sI 'https://cdn.jsdelivr.net/gh/ASDAlexey/sundayrun@main/data/version.json' | grep -iE 'age|cf-cache'
# age: 0 / cf-cache-status: MISS — сброшено; растущий age — пуржил не тот ключ, повтори с @main
```

После этого — **hard-reload** страницы (`⌘⇧R`).

Purge работает по одному файлу — маски `/*` нет. Саму БД пурджить не нужно и бессмысленно: она
раздаётся не с CDN, а из деплоя.

#### Частый кейс: поменял данные в `data/` напрямую, а прод показывает старое

1. Закоммитить изменение в `data/`, **запушить** в `main`.
2. Обновить `sha` в `data/version.json` на **запушенный** коммит, где лежат новые данные
   (обычно текущий HEAD: `git rev-parse origin/main`), закоммитить + запушить.
3. Дождаться деплоя: БД читается с Pages, поэтому новые байты доезжают только вместе со сборкой
   (CI **не** игнорирует `data/**`). Пока sha-копия не выложена, сайт покажет баннер «результаты
   обновляются».
4. При необходимости сбросить кэш указателя: `curl '…/purge.jsdelivr.net/gh/ASDAlexey/sundayrun@main/data/version.json'`.
5. Hard-reload страницы.

Если баннер завис навсегда — обычно рассинхрон «указатель ссылается на коммит, чей деплой не
собрал sha-копию». Расклинивается ручным коммитом указателя на актуальный HEAD данных.

### Доимпорт старой истории

Старые забеги публикуются **от старых к новым**: примечания каждого события считаются из истории, накопленной предыдущими публикациями, отсечённой до даты события. Перепубликация той же даты идемпотентна — вклад события снимается и накатывается заново. Внутри одной партии мультизагрузки порядок выстраивается по датам автоматически.

### Локализация контента

PDF-протокол, авто-примечания («Первое участие», «ЛР…») и текст ВК-анонса **не локализуются** — это русскоязычные документы клуба, их формулировки фиксированы независимо от языка UI. Интерфейс размечен под i18n (source locale `ru`); en-локаль отключена 2026-07-05 по решению пользователя — разметка `i18n`/`$localize` сохранена, вернуть перевод можно, добавив локаль в `angular.json` и файл переводов.

## Шаринг и публикация в ВК

1. Мобильные: Web Share API Level 2 — `navigator.share({ files: [pdf] })`, системное меню само показывает Telegram/VK/WhatsApp/MAX; PDF генерируется на лету и уходит файлом.
2. Десктоп/fallback — где Web Share с файлами недоступен: PDF скачивается, а share-диалог соцсети (`vk.com/share.php`) открывается со ссылкой на сайт; файл прикрепляется вручную.
3. Всегда доступны «Скачать PDF» и «Скопировать описание».
4. **Публикация забега в ВК (админ)**: после генерации приложение составляет мини-описание — № пробега, дата, место, число участников, победители М/Ж (редактируемое). Кнопка «Поделиться в ВК» (`result-page.ts` → `openVk`) отдаёт **PDF файлом**: где браузер умеет шарить файлы — системное меню с PDF + текстом уходит прямо в приложение ВК; где не умеет — PDF скачивается, а `vk.com/share.php` открывается со ссылкой на сайт, чтобы файл прикрепить вручную (ВК не принимает файлы через share-URL).

## Происхождение данных

На старте забега организатор пользуется приложением-секундомером: на финише каждого бегуна делается отсечка времени. Приложение экспортирует отсечки в xlsx (Name, Total, Avg/lap, Avg/km, Lap 1, Lap 2) — этот файл и загружается на сайт.

  state/                             # signal store мастера: участники, события, черновики партии
  features/                          # home | races | race | records | athlete | year | versus |

**Публичные страницы (маршруты без guard'ов).**

- `/` — лендинг: hero, объявление организатора, персональная карточка выбранного участника, 3 последних забега, кнопка «Все забеги», карта трассы, карточка «Общая статистика» (материализована в БД).
- `/races` — полный список забегов от свежего к старому: дата, № пробега, число участников, агрегаты 5 км (финишёры, среднее, лучшие и медианы М/Ж), график «динамика 8 недель», «Протокол онлайн», PDF, шаринг.
- `/races/:slug` — онлайн-протокол забега: шапка события с погодой, таблица на virtual scroll (№, спортсмен, время 2,3/5, темп, пол, места М/Ж с гэпом до следующего, клуб, участий, примечания и чипсы), ссылка на PDF; имя ведёт на страницу атлета. Некорректный slug (не `YYYY-MM-DD`) не доходит до БД — сразу «не найдено».
- `/records` — зачёты М/Ж с поиском и фильтрами по году и полу, вкладки рейтинга и «Гонки за сезон» (bump chart, deep link `?view=…`), номинации (погодные рекорды, пейсинг, рекорд первого круга, короли и королевы трассы).
- `/year` и `/year/:year` — итоги года: бейджи, «Прогресс года», ранги сезона.
- `/athletes/:key` — страница атлета: участия/финиши, рекорды за всё время и по годам, все забеги с фильтрами и сортировками, карточки «Форма», «Цифры за всё время», «Раскладка», «Легенда трассы», «Соперники», «Мем-пороги», бейджи и погодные ЛР. Прежний путь `/athletes` редиректит на `/records`.
- `/vs`, `/vs/:left`, `/vs/:left/:right` — очные встречи двух участников (общие 5-км финиши, счёт, флажки пейсинга); шарится ссылкой.
- `/guide` — «Фишки»: как считается каждая метрика и бейдж.

Публичные маршруты **пререндерены в статику** (`app.routes.server.ts`, `@angular/ssr`, `outputMode: static`): параметризованные `/races/:slug` и `/year/:year` перечисляют slug'и и годы из локального `.db` на билде через Node-адаптер (`github/protocol-db-node.ts`). Страницы атлетов и `/vs` остаются client-rendered — запекать каждый профиль значит дублировать архивные агрегаты в каждую страницу (см. [PERF_DB_REQUESTS.md](./PERF_DB_REQUESTS.md)). Мастер организатора грузится лениво (тянет xlsx/pdf-машинерию), остальные страницы — eager: lazy-чанк перерисовывал бы оболочку и сдвигал футер (CLS).

**Роли.** Обычные посетители — только просмотр. **Админ** (организатор, у которого в localStorage сохранён GitHub-токен) заходит на `/admin`: токен, объявление, кнопка «Загрузить забег» (мастер `/upload → /preview → /result`, guards не пускают на шаг без данных и без токена) и удаление ошибочно загруженного забега. `/admin` устроен в две колонки с общим dropzone и виртуальным списком забегов; `PendingArchiveService` держит оптимистичные плейсхолдеры «публикуется…» и прячет удалённые строки, пока запиненная БД не догонит. Никакого сервера аутентификации не нужно: право записи даёт сам токен GitHub.

**Ошибки и протухшие чанки.** Глобальный `NotificationService` (MatSnackBar) + `NotifyingErrorHandler` и `RouteErrorNotifier` в `app.config` показывают сбои вместо тихого залипания. Протухший lazy-чанк после деплоя один раз авто-перезагружает вкладку (loop-guard в sessionStorage).

## Правила проекта

- Компоненты: standalone, OnPush, `signal()`/`computed()`, `inject()`, `#private` в сервисах, `readonly` наружу.
- `.claude/rules/ts-files.md`: константы → `.constant.ts` (UPPER_SNAKE_CASE), enum'ы → `as const` + union в `.enum.ts`, интерфейсы → `.interface.ts`, типы → `.type.ts`.
- `.claude/rules/spec-files.md`: моки в `.mock.ts`, минимум `it()`-блоков при 100% покрытии, без `async beforeEach`.
- Запрещён `as` (`consistent-type-assertions: 'never'` в проде) — маппинг значений БД через `asString`/`asNumber`/`asNumberOrNull`/`asGender` из `protocol-db-row.ts`.
- `no-restricted-globals`: никаких глобальных `document`/`window`/`setTimeout` — инжектить `DOCUMENT`, таймеры брать из Angular-контекста.
- SCSS: только CSS-переменные (hex запрещён), типографика только через миксины `t.text()`, BEM `block__element_modifier`, transition только `var(--transition-time)`.
- Время — только целые миллисекунды; системные часы в доменной логике не читаются (даты приходят ISO-строками).
- Коммиты — только вручную пользователем.
