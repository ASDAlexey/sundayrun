# Backend: бесплатный хостинг + бэкап (Rust + Postgres)

План перехода с клиентского SQLite (sqlite-wasm-http) на серверный API
**Rust + PostgreSQL** с бесплатным хостингом, доступным из РФ, и защитой данных
через автобэкап наружу.

Статус: черновик плана. Код пишется отдельно.

Актуальность: §1–§4 писались до августа 2026 и исходят из Oracle Always Free как
выбранного хостинга. **§5 — свежая ревизия рынка (23.08.2026)**: лимиты Oracle с тех
пор урезали вдвое, зато появились проверенные российские варианты. Начинать чтение
про выбор площадки стоит с §5, а §2 воспринимать как исторический контекст решения.

---

## 1. Целевая архитектура

Фронт (Angular) перестаёт тянуть SQLite по HTTP range-запросам и ходит в обычное
REST API. Вся боль клиентского SQLite (range-запросы, патч размера под gzip
GitHub Pages, VFS) исчезает в момент появления серверного API — независимо от того,
какая БД внутри.

```
Angular SPA  ──HTTPS──>  Rust API  ──>  PostgreSQL
                          (axum)         (~20 МБ данных)
```

### Стек API

- **axum** — веб-фреймворк
- **sqlx** (Postgres, async, compile-time проверка запросов) + `sqlx migrate`
- **utoipa** + **utoipa-swagger-ui** — OpenAPI из `#[derive]`, Swagger UI на `/swagger-ui`

`Cargo.toml` (основное):

```toml
[dependencies]
axum = "0.8"
tokio = { version = "1", features = ["full"] }
sqlx = { version = "0.8", features = ["runtime-tokio", "postgres", "macros", "migrate", "chrono"] }
utoipa = { version = "5", features = ["axum_extras", "chrono"] }
utoipa-swagger-ui = { version = "8", features = ["axum"] }
serde = { version = "1", features = ["derive"] }
```

### Заметка про SQLite vs Postgres

Для 20 МБ read-mostly данных Postgres — избыточен (idle ест ~80–150 МБ RAM), и на
микро-хосте SQLite был бы легче. Выбран Postgres сознательно: нормальный SQL,
миграции, конкурентная запись на будущее. На хосте закладывать ≥1 ГБ RAM.

## 2. Хостинг

### Реальность «бесплатно + РФ + Postgres»

Надёжного «бесплатно навсегда» с persistent-сервисом **без иностранной карты** —
практически не существует. Всё по-настоящему бесплатное навсегда требует карту на
верификации. Fly.io / Render / Railway / Shuttle — иностранная карта + часть
блокируется/тормозит из РФ.

### Вариант A (выбранный): Oracle Cloud Always Free

Доступен, т.к. есть иностранная (EUR) виртуальная карта **«Плати по миру»**
(верификация — возвратный холд ~$1).

Что даёт бесплатно навсегда (не триал):

- **4 ARM-ядра Ampere A1 + 24 ГБ RAM** — можно резать на несколько VM
  (напр. 2 × 2 ядра/12 ГБ или 4 × 1 ядро/6 ГБ) → «несколько серверов в будущем»
- **+ 2 AMD micro-VM** (1 ГБ) тоже always-free
- **200 ГБ диска**, публичный IP

**Регион (home region):** Frankfurt / Amsterdam / Stockholm (~40–60 мс до РФ,
не блокируется). Выбирается один раз и не меняется.

**Сборка Rust:** под `aarch64` (A1 — это ARM, не x86). Multi-stage Dockerfile,
статик-бинарь musl.

Раскладка на одном A1 VM (Ubuntu 22.04, ARM64), docker-compose:

```
caddy      → авто-HTTPS (Let's Encrypt), проксирует на api
rust-api   → axum + sqlx + utoipa (Swagger на /swagger-ui)
postgres   → 20 МБ данных, том на block storage
```

### Подводные камни Oracle

1. **Карта на верификации.** Oracle строг к prepaid/виртуалкам — иногда режет.
   Пробовать; при отказе — план Б. Регистрация капризна по антифроду, бывает
   нужно 2–3 попытки.
2. **Reclaim простаивающих ARM-инстансов.** Лечится переключением аккаунта на
   **Pay As You Go** — в пределах free-лимитов денег не спишет, но reclamation
   отключается. Компромисс: PAYG возвращает зависимость от живой карты (см. §3).
3. **Лимиты урезали вдвое.** С 15.06.2026 Always Free ARM — не 4 OCPU / 24 ГБ, а
   **2 OCPU / 12 ГБ**, без публичного объявления. Плюс хроническое «out of capacity»
   при попытке поднять Ampere A1 в большинстве регионов. Подробности и источники — §5.

### План Б (если карту не примут)

- **Amvera Cloud** — РФ PaaS, git-push, managed Postgres, оплата картой РФ.
  Free-тир по факту тестовый: 0.1 vCPU / **0.1 ГБ RAM** / 2 ГБ — под API с базой мало.
- **Cloud.ru Evolution** — РФ, лимиты проверены в августе 2026, см. §5.
  Бесплатная ВМ **больше не выдаётся** новым аккаунтам; живой вариант — Container Apps.
- **Yandex Serverless Containers + YDB** — единственная связка, где и compute, и БД
  бесплатны и в РФ. Цена — YQL вместо Postgres, см. §5.
- **Дешёвый РФ-VPS** (Timeweb / Beget / RuVDS) ~150–250₽/мес — самый надёжный:
  один маленький VPS, docker-compose `api + postgres`, полный контроль.

## 3. Что если карта в будущем исчезнет — удалятся ли серверы?

**На чистом Always Free карта не списывается, поэтому её протухание само по себе НЕ
удаляет серверы.** Карта — пропуск на регистрацию (+ возвратный холд). Пока в
пределах бесплатного тира, биллинга нет → нет причины для блокировки.

| Режим аккаунта                                      | При мёртвой карте                                                                              |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| **Pure Always Free** (не апгрейдил)                 | Списаний нет → карта не нужна → серверы живут. **НО** остаётся риск reclaim простаивающего ARM |
| **Pay As You Go** (апгрейд ради отключения reclaim) | Выход за free-лимиты + карта не платит → письма → grace (недели) → suspend → terminate         |

Ловушка: PAYG убирает reclaim, но возвращает зависимость от живой карты.

### Выбор режима

- «Не думать» → **остаться на Always Free**, держать инстанс не пустым (постоянная
  нагрузка / крон), чтобы не попасть под reclaim. Карта тогда почти не важна.
- Гарантия от reclaim → **PAYG**, но держать на карте живой валидный метод.

### Главная защита — переносимость (важнее гаданий про карту)

Серверы должны быть **одноразовыми и воспроизводимыми**. Данных ~20 МБ — исчезновение
провайдера = ~10 минут передеплоя, а не потеря всего.

1. **Инфра в git** — `docker-compose.yml` + Dockerfile + миграции. Новый сервер
   поднимается одной командой на любом провайдере.
2. **Автобэкап БД наружу** — см. §4.
3. **Не держать состояние только у одного free-хоста.** Тогда «несколько серверов»
   = просто `docker compose up` + восстановление одного дампа.

## 4. Автобэкап БД на Яндекс.Диск (крон, только при изменениях)

Яндекс.Диск поддерживает **WebDAV** — заливка одной `curl`, без лишних бинарей.

Пароль — **не основной, а пароль приложения**
(Яндекс ID → Безопасность → Пароли приложений). С 2FA основной не пустит.

### Способ А — по хешу дампа (без изменений в коде API)

```bash
#!/usr/bin/env bash
set -euo pipefail

pg_dump --no-owner --no-privileges -U app appdb | gzip > /tmp/db.sql.gz
NEW=$(sha256sum /tmp/db.sql.gz | cut -d' ' -f1)
OLD=$(cat /var/backup/last.sha256 2>/dev/null || true)

[[ "$NEW" == "$OLD" ]] && { echo "нет изменений, пропуск"; exit 0; }

curl -sf --user "$YANDEX_LOGIN:$YANDEX_APP_PASSWORD" \
  -T /tmp/db.sql.gz \
  "https://webdav.yandex.ru/backups/appdb-$(date +%F).sql.gz"

echo "$NEW" > /var/backup/last.sha256
```

Нюанс: `pg_dump` теоретически может дать разный байт-порядок строк при тех же данных
(после VACUUM/реорганизации) → изредка «ложный» бэкап. Для маленькой стабильной БД
почти не встречается.

### Способ Б — по маркеру записи (100% точно)

API — единственный писатель, поэтому бампает счётчик на каждый мутирующий запрос:

```sql
CREATE TABLE meta (key text primary key, val bigint);
-- в каждом POST/PUT/DELETE:  UPDATE meta SET val = val + 1 WHERE key = 'writes';
```

Скрипт сравнивает `SELECT val FROM meta WHERE key='writes'` с сохранённым числом —
дампит только при росте. Без ложных срабатываний, не зависит от капризов `pg_dump`.

**Рекомендация:** старт на способе А (ноль изменений в коде). Нужна идеальная
точность — добавить маркер Б (5 строк в API).

### Крон + ротация

```
0 3 * * * /opt/backup.sh >> /var/log/backup.log 2>&1
```

Ротация: держать последние ~14 дампов, старые удалять (WebDAV `DELETE` или
`rclone delete --min-age`). Альтернатива `curl` — `rclone` (backend «Yandex Disk»,
удобнее ротация и ретраи, нужен один раз `rclone config`).

Восстановление: `gunzip -c appdb-YYYY-MM-DD.sql.gz | psql -U app appdb`.

## 5. Ревизия рынка — август 2026

Проверка по тарифным документам провайдеров на 23.08.2026. Разбор с источниками:
[артефакт «Бесплатный сервер для пробега»](https://claude.ai/code/artifact/a9895e4f-8b84-4b2c-81ec-edf215defad8).

### Главный вывод

Полностью бесплатной связки «российский сервер 24/7 + Postgres» не существует.
Каждый бесплатный тариф отдаёт что-то одно: либо процессорное время, либо диск,
либо базу. Бесплатные **связки** есть, но обе требуют компромисса — либо не-Postgres,
либо БД за рубежом.

### Реальный масштаб задачи

Цифры архива на дату ревизии — против оценки «~20 МБ» из §1:

| Метрика      | Факт   |
| ------------ | ------ |
| Файл БД      | 1,2 МБ |
| Забегов      | 275    |
| Результатов  | 2577   |
| Участников   | 274    |
| Записей в БД | ~1/нед |

Требование к серверу: 0.1 ядра, 512 МБ RAM, 1 ГБ диска. Postgres здесь нужен не
ради нагрузки, а ради удобства (нормальный SQL, миграции, транзакции вместо
переписывания SQLite-файла через git-коммит). Значит подойдёт **любая** база с
внятным SQL — не обязательно именно Postgres.

### Российские площадки

**Cloud.ru Evolution · Container Apps** — рабочий вариант. Любой Docker-образ без
Kubernetes и без ВМ, публичный HTTPS-адрес включён (платный IP не нужен),
масштабирование в ноль.

- Бесплатно: 25 vCPU×час + 50 ГБ RAM×час в месяц на всю организацию
- Object Storage: 15 ГБ + 10 ТБ исходящего трафика
- Artifact Registry: 0,16 ₽/ГБ/мес → образ 15 МБ ≈ **0,04 ₽/мес** (единственная не-нулевая строка)
- Требуется положительный баланс ≥ 100 ₽ (не абонплата, но и не совсем ноль на входе)

⚠️ Расхождение, которое надо уточнить в поддержке: правила акции называют
**120 vCPU×часов и 480 ГБ RAM×часов**, документация сервиса — 25 и 50. От этого
зависит, можно ли держать контейнер поднятым круглосуточно: при 120 контейнер
0.1 vCPU влезает в 24/7 (720 ч × 0.1 = 72), при 25 — только scale-to-zero.

**Cloud.ru Evolution · бесплатная ВМ** (2 vCPU / 4 ГБ / 30 ГБ SSD) — **отпала**.
Дословно: «создание новой бесплатной виртуальной машины недоступно для пользователей,
которые зарегистрировались после 30 июня 2026 года». Плюс публичный IP в тир не входил.

**Yandex Cloud · Serverless Containers + YDB** — единственный полностью российский
и полностью бесплатный вариант:

- Контейнеры: 1 000 000 вызовов + 10 ГБ×час RAM + 5 vCPU×час
- YDB serverless: 1 000 000 операций + 1 ГБ хранения
- Object Storage: 1 ГБ / 10 000 PUT / 100 000 GET; SmartCaptcha: 10 000 проверок

Цена — YDB не Postgres: язык YQL, своя транзакционная модель, нет `psql` и привычных
миграционных инструментов. Rust-клиент официальный (`ydb-rs`).

**Рег.облако / VK Cloud / Timeweb** — не бесплатный тариф, а стартовые бонусы
(VPS до 6 мес / 4000 ₽ бонусов / 10 дней теста). Для многолетнего проекта не подходит.

### Зарубежные площадки

| Площадка               | Статус на 08.2026                                                                        |
| ---------------------- | ---------------------------------------------------------------------------------------- |
| **Oracle Always Free** | Лимиты урезаны вдвое 15.06.2026 (2 OCPU / 12 ГБ), Ampere почти всегда занят              |
| **Cloudflare + D1**    | 100k запросов/день, D1 = SQLite 5 ГБ, карта не нужна — но `workers.dev` из РФ нестабилен |
| **Fly.io**             | Free tier закрыт для новых аккаунтов, требуется карта                                    |
| **Railway**            | $1 кредита — несколько часов работы в месяц                                              |
| **Render**             | Web-сервис засыпает через 15 мин, бесплатная БД удаляется через 30 дней                  |

### Бесплатные базы, которые не истекают

| База       | Объём                        | Движок          | Карта    | Подвох                              |
| ---------- | ---------------------------- | --------------- | -------- | ----------------------------------- |
| Yandex YDB | 1 ГБ · 1 млн операций/мес    | YQL             | нужна    | не Postgres, свой диалект           |
| Turso      | 5 ГБ · 500 млн чтений строк  | libSQL (SQLite) | не нужна | зарубежный, edge-модель             |
| Neon       | 0,5 ГБ на проект (до 100)    | PostgreSQL      | не нужна | засыпает через 5 мин, старт 0,3–1 с |
| Supabase   | 500 МБ · 5 ГБ трафика        | PostgreSQL      | не нужна | проект встаёт после 7 дней тишины   |
| Aiven      | 1 ГБ · выделенный 1 CPU/1 ГБ | PostgreSQL      | не нужна | урезали с 5 ГБ до 1 ГБ, нет HA      |

**Turso** заслуживает отдельного взгляда: libSQL — форк SQLite, написанный на Rust.
Для проекта, уже живущего на SQLite, это самый дешёвый переезд: схема и запросы те же,
меняется транспорт. 5 ГБ против нынешних 1,2 МБ — запас в ~4000 раз.

### Три сборки

| Сборка             | Стек                                                         | Цена          | Компромисс                       |
| ------------------ | ------------------------------------------------------------ | ------------- | -------------------------------- |
| **Полностью в РФ** | Rust в Serverless Containers + YDB + Object Storage          | 0 ₽           | YQL вместо Postgres              |
| **Привычный SQL**  | Rust в Cloud.ru Container Apps + Turso/Neon + Object Storage | ≈ 0 ₽         | БД физически за рубежом          |
| **Свой сервер**    | РФ-VPS 1 ядро / 1 ГБ, `api + postgres` в docker-compose      | 150–250 ₽/мес | платно, зато без лимитов и акций |

### Риски бесплатных тарифов

- **Free tier — акция, а не обязательство.** У Cloud.ru действует до 31.12.2026.
  Бесплатную ВМ там уже закрыли 30.06.2026 — так же может закрыться и остальное.
- **Неактивность убивает.** Cloud.ru: приостановка аккаунта после 90 дней без
  активности, удаление после 180. Supabase: остановка проекта после 7 дней тишины.
- **Появляются обязанности, которых сейчас нет.** Статику на Pages нечему уронить;
  сервер приносит бэкапы, обновления безопасности, миграции и риск падения перед
  воскресным забегом. Отсюда важность §3 (переносимость) и §4 (автобэкап).

### Промежуточный шаг без сервера

Если главная боль — медленная публикация из-за git-коммита, заметная часть снимается
**без бэкенда вообще**: файл БД в объектном хранилище вместо git-репозитория
превращает публикацию из «коммит + CI + инвалидация кеша» в один HTTP-запрос.
Секунды вместо минут при неизменной архитектуре. 15 ГБ Cloud.ru или 1 ГБ Яндекса
покрывают базу 1,2 МБ с абсурдным запасом.

Полноценный бэкенд оправдан там, где нужны вещи, которых статика не даёт в принципе:
приём данных от пользователей, авторизация, живые запросы, формы.

### Что проверить перед стартом

1. Уточнить в поддержке Cloud.ru реальные лимиты Container Apps (25 vCPU×ч или 120).
2. Проверить, доступен ли free tier Container Apps при регистрации после 30.06.2026 —
   по аналогии с ВМ дата отсечки могла появиться и здесь.
3. Замерить холодный старт и стабильность публичного адреса контейнера из РФ-сетей —
   единственное, чего нет в документах.
4. Решить до написания кода: Postgres как самоцель или «нормальная база вообще».
   От ответа зависит выбор между YDB (бесплатно и в РФ) и Turso/Neon (привычно, но за рубежом).
